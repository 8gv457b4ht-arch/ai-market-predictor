## 2. Подробности

### A1. Планировщик GitHub Actions — Высокая
**Факты.** Расписание `1,16,31,46 * * * *`. С 09:46 до 11:31 было 8 слотов — выполнено 8 запусков, все успешны.
Опоздание старта относительно слота: 8, 5, 12, 13, 11, 7, 10, 7 мин. Длительность запуска ≈ 1,3 мин.
Прогнозы 15m: сделано 7 из 8 ожидаемых по каждому активу, пропущена свеча 10:15 UTC.
Задержка решения после закрытия свечи: медиана 569 с, максимум 739 с (15m); для 1h первая — 3362 с.
**Причина.** Cron GitHub работает «по возможности»; при опоздании 12–13 мин два соседних запуска (10:28 и 10:44)
попали так, что свеча 10:15 (закрыта в 10:30) была уже не последней закрытой ко второму запуску.
**Последствия.** Пропуски в журнале; прогноз приходит, когда от горизонта (4 свечи = 60 мин) прошло ~16 %.
Пропущенные свечи нигде не отмечались.
**План.** (1) Внутри запуска ждать ближайшего закрытия свечи (до 16 мин) при открытом WebSocket и прогнозировать
сразу после закрытия — задержка падает с ~10 мин до секунд, пропуски почти исчезают без изменения расписания.
(2) Явно записывать пропущенные свечи (`missed_slot`) и показывать их в журнале и статусе. (3) Для настоящей
непрерывности — отдельный постоянный сервер (п. A13).

### A2. Нет истории проверок бирж — Высокая
**Факты.** `system_state.exchange_probes` хранит только последнюю проверку. Частота ошибок REST/WS, доля
блокировок и задержек за час/сутки неизвестны.
**План.** Таблица `source_checks` (каждая проверка REST и WS: время, биржа, тип, успех, вид ошибки, задержка,
расхождение часов). Экспорт долей успеха за 1 ч и 24 ч в `state.json`, показ в панели состояния.

### A3. Статусы — Высокая
**Факты.** Использовались метки RUNNING/VERIFIED/PARTIAL/DEGRADED; данные бэкенда, проверенные раз в 15 мин,
могли выглядеть как живые.
**План.** Единая шкала: LIVE (поток с проверенными метками времени < 30 с), DELAYED (данные верны, но получены
периодически/с опозданием), STALE (старше допустимого), OFFLINE (источник недоступен), ERROR (сбой обработки).
Панель из 12 пунктов: API, Binance, Bybit, OKX, исторические данные, WebSocket, база данных, модель, новости,
последний успешный прогноз, последний запуск фонового процесса, последняя резервная копия.
Данные периодического бэкенда никогда не получают LIVE.

### A4. Хранение и восстановление — Высокая
**Факты (проверено).** `PRAGMA integrity_check` = ok; схема 2; пропусков и смещений свечей нет ни на одной
бирже/паре/таймфрейме; дубликаты исключены первичным ключом. 8 файлов моделей на месте и загружаются.
Одна резервная копия (09:37, интервал 6 ч), её целостность ok, восстановление в отдельный файл проверено.
**Проблемы.** При старте запуска целостность не проверяется; при повреждении БД нет автоматического
восстановления из копии; шаг сохранения пушит состояние даже после ошибки цикла; ветка `data` — один
коммит, перезаписываемый `--force` (предыдущего состояния в git нет; спасают только копии внутри него);
контрольные суммы файлов моделей не проверяются.
**План.** Проверка целостности при старте → при сбое автоматическое восстановление из последней исправной копии
(с записью события); проверка целостности и загрузки моделей перед сохранением; сохранение «последнего
исправного» состояния; копии с проверкой после записи; SHA-256 файлов моделей в реестре.

### A5. Откат модели — Средняя
**План.** Команда `scripts/state_tool.py rollback <ключ>` (возврат предыдущей архивной версии в production
с записью события), запуск вручную из Actions; отчёт об изменении модели: метрики до/после, по режимам рынка.

### A6. Качество прогнозов — Высокая
**Факты (реальные данные, walk-forward, ~1970 прогнозов вне выборки на модель).** Log loss модели против
наивной (базовые частоты): BTC 15m 0,849 vs 0,862; BTC 1h 1,045 vs 1,048; ETH 15m 0,947 vs 0,950;
ETH 1h 1,068 vs 1,054 (хуже). Улучшение 0,3–1,5 % — в пределах шума. В живом журнале 20 прогнозов, все
NO TRADE; из 6 проверенных — 2 верных воздержания, 4 пропущенных движения (ETH 15m три раза DOWN).
**Причина.** На горизонте 1–4 ч направление цены почти не предсказуемо этими признаками; FLAT по определению
(порог ≥ 25 б.п. издержек) составляет 48–67 %.
**План.** Исследование на реальных данных с отложенным периодом (раздел 3 задания), причина NO TRADE
«MODEL NOT BETTER THAN BASELINE», когда модель не лучше baseline вне выборки. Пороги не снижаются.

### A7. Смещение выбора — Средняя
Исправление калибровки придумано после анализа той же истории, на которой затем оценено. Оценка «после»
поэтому оптимистична. **План:** новые процедуры сравниваются на последнем отложенном отрезке, который не
использовался ни для разработки, ни для настройки; результат подтверждается живым журналом.

### A8–A9. Разметка — Низкая
Независимая перепроверка всех 6 разрешённых прогнозов по свечам из БД: 0 расхождений (цена старта, цена
цели, время цели = свеча + 4 бара, направление по порогу). Утечки по старшим таймфреймам нет (признаки
присоединяются по времени закрытия), purge = горизонт в walk-forward, новости берутся только опубликованные
до закрытия свечи, калибровка — на последних 20 % обучающего окна.
Недочёты: заполнение порога медианой всей выборки и сдвиг по строкам. **План:** заполнять порогом издержек;
метка только если время цели ровно `t + h·bar`.

### A10–A11. Интерфейс — Высокая/Средняя
Проверены браузерными тестами (офлайн-режим в CI, серверный — локально): графики, вкладки, фильтр журнала,
настройки, тест соединений, ширина 390 px без горизонтальной прокрутки. Не хватает: перевода, фильтров по
активу/модели/периоду, кодов причин NO TRADE, ожидаемых издержек и чистого результата, времени проверки,
факторов прогноза, отчёта об изменениях модели.

### A12. Уведомления — Средняя
Секреты берутся только из GitHub Secrets/окружения, в код и в публичный JSON не попадают (проверено поиском
по экспорту). Дубли при повторных запусках исключены (последний отправленный id хранится в БД).
Не хватает: минимальных условий (уверенность, таймфрейм, только сигналы), проверки устаревания перед отправкой,
содержимого «причина и качество данных». Реальная доставка не проверялась (нет секретов).

### A13. Работа 24/7 — честная оценка
GitHub Actions запускает цикл раз в 15 мин с опозданием; WebSocket открыт ~45 с. Это **не** постоянный
WebSocket и не 24/7 сбор данных. Нужен отдельный постоянно работающий процесс (VPS/Docker) — конфигурация
будет подготовлена; пока он не запущен на реальном сервере, круглосуточная работа не считается проверенной.

### A15. Доступность бирж (с серверов GitHub, США)
